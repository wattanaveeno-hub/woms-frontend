## 3. แผน migration ที่อาจต้องใช้ (ยังไม่ทำ — ต้องได้รับอนุญาตก่อน)

### M-01 รวมกลุ่มแชทซ้ำ (ทำเมื่อ PF-01 > 0 เท่านั้น)
1. **เหตุผล:** มีกลุ่มซ้ำแล้ว unique index สร้างไม่ได้ · Round 2 กันการสร้างซ้ำเพิ่มด้วย op lock แล้ว แต่กลุ่มซ้ำเดิมยังอยู่
2. **Dry-run:** รัน PF-01 ได้รายการ groupKey ที่ซ้ำ + จำนวนข้อความต่อกลุ่ม · ข้อความอ้างด้วย groupKey (ไม่ใช่ `_id` ของกลุ่ม) จึงไม่ต้องย้ายข้อความ
3. **จำนวนที่คาด:** เอกสารที่จะลบ = Σ(n − 1) ต่อ groupKey ที่ซ้ำ · `group_messages`, `group_reads`, `group_files` เปลี่ยน 0 เอกสาร
4. **Backup:** `mongodump --collection chat_groups` + backup เต็มที่ทดสอบ restore แล้ว
5. **ขั้นตอน:** เก็บเอกสารที่ `createdAt` เก่าสุดต่อ groupKey ลบที่เหลือ แล้วสร้าง index `uniq_group_key` (unique)
6. **Rollback:** `mongorestore --collection chat_groups` จาก dump (ไม่กระทบข้อความ)
7. **หยุดก่อน production** และขออนุญาตเป็นลายลักษณ์อักษร

### M-02 Serial/สัญญาซ้ำ (เมื่อ PF-08 > 0)
ต้องให้ลูกค้าตัดสินว่า Record ใดถูก — **ไม่มีกติกาอัตโนมัติ** · ทำทีละรายการผ่านหน้าจอที่มีอยู่ (ยกเลิกสัญญา/แก้ Serial) พร้อม Audit Log

### M-03 ประเภท/รูปแบบ/รุ่นเครื่อง (D-07)
รอ mapping จากลูกค้า · ต้องมี dry-run ที่แสดงจำนวนเครื่องที่เปลี่ยนต่อรุ่น, backup, rollback ก่อนอนุมัติ

### M-04 Unique index "เครื่องละ 1 สัญญามีผล" (ข้อเสนอ — ยังไม่ได้ทำ ไม่ได้รันกับข้อมูลใด)
- **เหตุผล:** ผู้ตรวจอิสระพบเส้นทางที่ทำให้สัญญามีผลซ้ำต่อเนื่อง 6 เส้นทาง (R2-F03, F04, F09, F12, F14, F15) — ตอนนี้ปิดด้วย op lock ในโค้ดทุกเส้นทางที่รู้จัก แต่เส้นทางใหม่ในอนาคตอาจหลุดอีก · index บน DB บังคับได้ทุกเส้นทาง
- **ข้อมูลที่ต้องมีก่อน:** ฟิลด์ `serialKey` (ตัวพิมพ์ใหญ่) ในสัญญาทุกฉบับ · ผล PF-08 = 0 (ไม่มีสัญญามีผลซ้ำ) · ตัดสินเรื่องสัญญา COMPLETED ที่ยังอยู่ในระยะ (ปัจจุบันนับว่ามีผลในโค้ด แต่ partial index ใช้เงื่อนไขตามวันไม่ได้)
- **ขั้นตอน (ร่าง):** dry-run นับสัญญาที่ต้องเติม `serialKey` และคู่ที่ชน → backup `contracts` → เติม `serialKey` → สร้าง `{serialKey:1}` unique partial `{status:{$in:["DRAFT","ACTIVE"]}}` → รัน PF-08 ซ้ำ
- **Rollback:** drop index + `$unset serialKey` (หรือ restore จาก dump)
- **หยุดก่อน production** · ต้องได้รับอนุมัติจาก Repository owner และ Deployment owner
