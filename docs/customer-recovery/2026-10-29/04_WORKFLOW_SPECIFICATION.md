# 04 · Workflow Specification (To-Be ตามที่ implement แล้ว)

อธิบายพฤติกรรมของระบบหลังแก้ (backend `992072c`, frontend `ab465af`) · ข้อที่ยังรอลูกค้ายืนยันระบุไว้ชัด ไม่ถือเป็นกติกาที่ตกลงแล้ว

## Workflow 1 — ติดตั้งขาย / เช่า (WF-01, WF-02, INST-01..03, QUE-01)

| ขั้น | ผู้ทำ | UI | API | สถานะคิว | ผลใน DB |
|---|---|---|---|---|---|
| 1 เปิดคิว | เซลล์ (หรือ Admin แทนเซลล์) | `/service-queue/new` · ประเภทงาน "ติดตั้ง" → ประเภทย่อย "เช่า/ขาย" · ลูกค้า/สาขา (เพิ่มสาขาได้) · เครื่องจากคลังหรือเครื่องใหม่ + เครื่องกรอง/ประกัน(ขายเท่านั้น)/เงื่อนไข PM ต่อเครื่อง | `POST /api/service-queue` (คิวใหม่ `INSTALL` ไม่ระบุเช่า/ขาย → 400) | `WAIT_ASSIGN` | `service_queues` + event `CREATE` + การ์ดกลุ่มเช็คคิว + แจ้ง Admin |

คิวเลื่อนงาน (mode `RESCHEDULE`, ผูก JN เดิม): ขั้น 5' ไปที่ `READY_TO_OPEN` เช่นกัน แล้ว Admin กด "ยืนยันส่งงานเดิมกลับ" (`RELEASE_RESCHEDULE`) — ใบงานเดิมกลับเป็น OPEN วันนัด/ช่างใหม่ ไม่สร้าง JN ใหม่ (ยืนยันโดย independent QA)

เปลี่ยนช่าง: ช่างเดิมได้ข้อความในกลุ่มของตน "Q-… · คิวนี้ถูกยกเลิกแล้ว–ไม่ต้องดำเนินการต่อ (… คิวหลักยังดำเนินต่อ …)" — เป็นการจบการมอบหมายเดิม ไม่ใช่ยกเลิกคิว (ไม่ส่งข้อความนี้เมื่อช่างกดไม่รับคิวเอง)

### กติกาฐาน PM จากการติดตั้ง (INST-03)
ตั้งเมื่อ **ปิดใบงานติดตั้งสำเร็จ** และแถวเครื่องนั้นระบุเงื่อนไข PM (`pmMode`) และมีรอบ (เดือน) > 0
- `lastPmDate` = วันที่ช่างบันทึกว่าเครื่องนั้นเสร็จ (`job_equipment.completedAt` เวลาไทย) — ไม่ใช่วันนัด
- ไม่ถอยวัน (ถ้ามี PM ที่ใหม่กว่าแล้วไม่เขียน) · แถวเดิมปิดซ้ำไม่ตั้งซ้ำ
- เก็บ `pmBaselineSource: INSTALL`, `pmBaselineJobId` · ประวัติเครื่องเป็น event `EDIT` "ฐาน PM จากการติดตั้ง… (ไม่ใช่การเข้าบริการ PM)" ไม่ใช่ event `PM` และไม่ตัดรอบ Package
- รอบถัดไป = `lastPmDate + pmIntervalMonths` (domain/pm.ts) เช่น เสร็จ 15 พ.ย. 2569 ทุก 3 เดือน → 15 ก.พ. 2570
- เปิดงาน / เลื่อน / ยกเลิก **ไม่** ตั้งฐาน PM
- ⚠ แหล่ง "วันที่ติดตั้งจริง" ยังรอลูกค้ายืนยัน (D-10)

## Workflow 2 — ตาราง PM → คิว → JN (PM-01..03)

| ขั้น | ผู้ทำ | UI / API | สถานะในตาราง PM (PM-02) |
|---|---|---|---|
| 0 | Admin สร้าง/อนุมัติ/ส่งตาราง | `/pm` (เดิม) | รอเสนอคิว |
| 1 | ช่างเปิดตาราง PM ของตน (ส่งแล้ว) เลือกรายการ กด "เสนอวันเวลา" | `POST /api/pm/plans/:id/items/:itemId/propose {date,time,note}` — เฉพาะช่างเจ้าของตาราง, ตาราง `SENT`, รายการ `PLANNED` ยังไม่มีคิว/ใบงาน | ช่างเสนอแล้วรอ Admin |
| 2 | ระบบสร้างคิว `source: "PM"` ผูก `pmPlanId/pmItemId`, เครื่องตัวเดิม, ลูกค้า/สาขา, ผู้เสนอ · การ์ดป้าย "งานจากตาราง PM" เข้ากลุ่มเช็คคิว + กลุ่มงานช่าง · แจ้ง Admin | จอง slot แบบ conditional update — กดซ้ำ/พร้อมกันได้คิวเดียว | |
| 3 | Admin รับคิว → ยืนยันลูกค้า (Admin ทำเอง ไม่มีเซลล์เจ้าของงาน) · ไม่ได้ → ขอวันใหม่ (คิวเดิม/รอบ PM เดิม) | เส้นทางคิวปกติ | รอลูกค้าคอนเฟิร์ม → ลูกค้าคอนเฟิร์มแล้ว รอ Admin เปิดงาน |
| 4 | Admin กดเปิดงาน | `POST /api/service-queue/:id/release` — ตรวจรายการ/ตารางก่อนออก JN (ตารางยกเลิก/รายการไม่ใช่ PLANNED → 409 ไม่มี JN กำพร้า) | เปิดงานแล้ว/รอดำเนินการ (`JOB_CREATED`, jobId) |
| 5 | ช่างทำงาน ปิดงานสำเร็จ | `POST /api/jobs/:id/close` | **เข้า PM แล้ว** (`DONE`) + `lastPmDate` เดินหน้า + รอบถัดไป |

กรณีพิเศษ
- ยกเลิกคิวก่อนเปิดงาน → รายการกลับ "รอเสนอคิว" (เก็บเลขคิวใน `cancelledQueueIds`) เสนอใหม่ได้
- ยกเลิกใบงาน PM → รายการกลับ "รอเสนอคิว" (เก็บเลขใบงาน/คิวเดิมเป็นประวัติ)
- ช่างไม่รับคิว → "ช่างไม่รับ — รอ Admin จัดช่าง"
- ระหว่างรายการอยู่ในคิว: ตัดออกจากแผน (409), ยกเลิก/ปิดรอบตาราง (409), ปุ่ม "สร้างใบงาน" ตรงจากตาราง (409)
- หลายเครื่องร่วมคิวเดียว: **ยังไม่รองรับ** (รอยืนยันขอบเขต D-12) — เสนอทีละรายการ

## Workflow 3 — ความสอดคล้องของข้อมูล

Queue → JN → Job Machine → Machine Record → PM / Contract / Billing
- `service_queues.jobId` ↔ `jobs.queueId` (unique partial index `uniq_job_queue`)
- `service_queues.items[].jobEquipmentId` ↔ `job_equipment._id` · `equipmentId` = Machine Record ตัวเดิม (เครื่องไม่มี SN อ้าง Record เดิม ไม่สร้างซ้ำ)
- `pm_schedules.items[].queueId/jobId` ↔ คิว/JN · DONE จากการปิดงานเท่านั้น
- `quotations.jobId` ↔ JN (1 ใบเสนอราคาต่อใบงาน · ลูกค้าตรงกัน · ไม่สร้าง JN เพื่อผูก)
- `contracts.serial/model` = ค่าจาก Machine Record เมื่อพบ Serial ในคลัง
- บิลช่างอ้าง Job Machine (เดิม) — ไม่เปลี่ยนในรอบนี้
